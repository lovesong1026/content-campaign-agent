# 内容任务规划 Agent：需求与验收约定 v1

状态：实现前的设计基线，尚未经过代码或真实模型运行验证。

需求来源：[README.md](../README.md)。本文中的时间、费用、状态及重复执行规则属于本项目的设计选择，不是原题指定的唯一答案。后续如需修改，应同步修改代码、测试与评估文档，并说明原因。

## 1. 用户、目标与完成标准

用户是需要制定内容活动方案的运营人员。用户提供活动主题、预算和方案交付截止时间；系统检索合成素材，生成脚本，估算费用，依据实际工具结果调整方案，最后保存可行方案，或说明未完成原因。

一次任务只有同时满足以下条件才能标记为成功：

1. 方案与用户主题相关，使用可追溯的素材，包含生成的脚本。
2. 当前版本方案已通过成本估算，预计总费用不超过预算。
3. 方案在约定的交付截止时间内保存成功，保存工具返回可核对的方案标识与存储位置。
4. 任务状态、步骤状态、费用记录和工具实际结果一致。

模型声称“已完成”、生成了脚本或成本合规，都不能单独证明任务成功。无法完成时，应返回真实状态、失败原因、已成功的结果及可计算的缺口。

## 2. 范围与最小交互

### 2.1 本期范围

- 采用 CLI、单 Agent、顺序调用工具，支持真实模型入口和独立的离线 Mock 入口。
- 实现素材检索、脚本生成、成本估算、方案保存四个本地业务工具。
- 提供合成素材、模拟工具费用及耗时规则；支持在测试中注入工具故障。
- 持久化任务记录、费用账本、Trace 和已保存方案，支持查询已有任务结果。
- 覆盖五类必验场景，提供可执行测试和实际运行证据。

本期不要求界面、线上部署、多 Agent、真实业务服务或失败步骤续跑；不要求多进程并发执行与进程崩溃后的自动恢复。无需接入 Langfuse 等外部平台，Trace 可以保存在本地。

真实模型已确定使用 DeepSeek API 的 Flash 模型，API 模型标识为 `deepseek-flash`，接口基础地址为 `https://api.deepseek.com`，密钥通过 `DEEPSEEK_API_KEY` 配置。DeepSeek 提供 OpenAI 兼容接口并支持工具调用，客户端采用 OpenAI Python SDK 的 `AsyncOpenAI`；具体协议、思考模式及依赖版本在方案文档中定义，并通过实际接入验证。参见 [DeepSeek 接入文档](https://api-docs.deepseek.com/)与[工具调用文档](https://api-docs.deepseek.com/guides/tool_calls/)。目前尚未执行模型请求，不能据此宣称接入验证完成。

### 2.2 输入约定

| 字段 | 必填 | 规则 |
| --- | --- | --- |
| `theme` | 是 | 非空字符串，去除首尾空白后至少有一个字符 |
| `budget` | 是 | 非负十进制数，最多两位小数，单位为模拟费用单位 |
| `deadline` | 是 | ISO 8601 时间；接受显式时区，省略时区时按北京时间 `Asia/Shanghai` 解释 |
| `task_id` | 否 | 不提供时生成新 ID；提供时用于识别同一任务 |

文档示例优先使用带时区的时间，如 `2030-01-01T10:30:00+08:00`。测试应固定任务起点，使示例不会因真实日期变化而失效。缺失项不能由模型自行编造。

### 2.3 输出约定

每次执行或查询至少展示：

- 任务 ID、输入、运行模式及任务状态。
- 当前计划、步骤依赖与状态，以及已有步骤的实际结果或错误摘要。
- 已发生工具费用、当前方案预计费用、预计总费用和剩余预算。
- 任务起点、累计模拟耗时、模拟当前时间和截止时间。
- 成功时提供已保存方案的 ID 与路径；未完成时提供原因、缺失项或缺口。
- 可定位到本次执行的 Trace 路径。

当前尚无有效成本估算时，方案预计费用、预计总费用和缺口应显示“未知”，不能以 0 冒充已估算结果。

## 3. 决策循环与执行边界

模型在每轮收到用户目标、约束、当前计划、已有结果、费用与时间余量，选择一个工具动作或结束任务。工具执行后，真实返回值或错误作为下一轮观察输入。

预设流程可以安排基础依赖，但以下决定必须来自模型对实际观察的响应：

- 估算超预算后，选择降低内容规模、替换素材、重写脚本或明确停止。
- 工具出错后，选择重试、可行的替代动作或明确停止。
- 已有方案无法按时交付时，选择更短的有效路径或明确停止。

代码负责参数校验、费用及时间计算、依赖校验、保存门禁、状态持久化和上限控制。这些确定性检查不能替代模型选择替代方案，也不能把失败改写成成功。

模型可以在可行方案找到后立即保存，无须穷举最优方案。成本不足或没有可用素材时，不允许虚构素材、脚本、估算或保存结果。

## 4. 截止时间规则

### 4.1 时间口径

截止时间约束的是“生成并保存方案”的交付时间。活动本身的拍摄、发布及投放时间不在本期调度范围内；预算仍可包含这些内容执行的预计费用，两者应分别展示。

- 任务校验通过、首次开始执行时，记录一次真实起点 `started_at`，同时记录时区；内部统一比较时间点，展示默认使用北京时间。
- 单次任务按顺序执行，不计算并行节省的时间。
- 采用耗时表中的模拟耗时，不要求程序实际等待；模型网络延迟不计入模拟业务耗时。
- 实际墙钟时间可单独记录，用于评估性能，不能混入模拟截止时间计算。

```text
模拟当前时间 = started_at + 所有已执行工具的模拟耗时之和
预计交付时间 = 模拟当前时间 + 当前候选路径中剩余必需工具的模拟耗时
```

### 4.2 边界与门禁

- 截止时间早于或等于任务起点时，没有执行窗口，返回未完成，业务工具不执行。
- 预计交付时间等于截止时间视为按时。
- 工具真正执行前，程序检查其完成时刻是否超过截止时间；超过则阻止执行，返回结构化观察供模型处理，不收取费用，也不累计耗时。
- 模型规划时必须包含成本估算和方案保存等剩余必需步骤，不能只检查下一步能否执行。
- 保存前必须再次检查：保存工具完成时刻不晚于截止时间。
- 已执行且失败的工具按完整模拟耗时累计，不能在重试时回退时间。
- 未执行的候选路径只是预测，不计入已消耗时间。

## 5. 费用规则

### 5.1 预算口径

所有金额使用十进制定点数或整数分计算，避免浮点误差。预算覆盖任务中的模拟工具费用，以及最终方案内容执行的预计费用。

```text
已发生工具费用 C = 所有实际执行的工具调用费用之和
方案预计费用 P = 当前方案内容制作、素材使用及投放等尚需费用
预计总费用 T = C + P
预算缺口 = max(0, T - budget)
```

`P` 是模拟业务执行的预计费用，本项目保存方案时不实际扣款。真实模型 API 费用不纳入模拟预算；如可获取，可单列统计并明确币种。

### 5.2 初始工具费用与耗时

实现时应将下表配置固化到 `data/`，作为工具执行及测试的共同依据。

| 工具 | 单次费用 | 模拟耗时 | 说明 |
| --- | ---: | ---: | --- |
| 素材检索 | 1.00 | 2 分钟 | 返回素材 ID、用途、授权及可用性等信息 |
| 脚本生成 | 2.00 | 5 分钟 | 根据已有素材生成新版本脚本与方案 |
| 成本估算 | 1.00 | 1 分钟 | 按费用规则估算指定版本，不能接受模型自报总价作为依据 |
| 方案保存 | 0.00 | 1 分钟 | 保存已通过门禁的方案并返回结果 |

素材与方案执行价格由合成材料和费用规则决定，不能为凑预算在运行中随意修改。测试如使用不同规则，必须保留该规则快照或版本。

### 5.3 记账与防止重复计算

- 实际执行的工具调用无论成功还是失败，均收取完整工具费用；再次执行重新收费。
- 参数不合法、未知工具或执行前被预算、时间、依赖检查阻止的动作，不算业务工具执行，不收费、不累计耗时，但记录拒绝原因。
- 调用前检查 `C + 本次工具费用 <= budget`，避免工具调用本身突破预算；最终是否可行仍需检查方案费用。
- 成本估算返回的 `T` 必须包含本次估算调用已发生的费用。剩余调用费用另行预测，不能漏算重写与再次估算的成本。
- 模型修改方案后，用新方案的 `P` 替换旧预测；历史 `C` 持续累计。多个候选方案的 `P` 不相加，因为最终只选择一个方案。
- 每次调用有独立账本项，账本只记一次；幂等读取已有结果不新增账本项。
- 保存工具费用为 0，因此成功估算后不再调用其他收费工具时，估算时的 `T` 就是保存时的预计总费用。若中途又执行了收费工具，保存门禁必须使用最新 `C` 重新计算。

例如，首次检索、生成脚本、估算共花费 4，方案预计费用为 8，则总费用为 12。预算为 10 时，模型改写脚本并再次估算，工具累计费用增加至 7；若新方案预计费用为 1，则总费用为 8，可以保存。这只是规则示例，不是已取得的运行结果，也不要求模型固定执行这条路径。

## 6. 重复执行规则

采用“同一任务返回已有记录”的最小幂等策略。

1. `task_id` 相同且规范化后的业务输入相同：返回已有任务状态、结果和 Trace，不发起新的模型或工具调用，不重复收费、不重复保存。
2. `task_id` 相同但业务输入不同：返回 `TASK_INPUT_CONFLICT`，不覆盖原任务、不产生费用。
3. 不提供 ID 或使用新的 ID：视为新任务。即使业务输入相同，也独立执行、计费和保存。
4. 同一 ID 的执行中请求只返回已有执行状态，不启动第二次执行。
5. 已停止、缺信息或未完成的任务同样遵循以上规则。本期不支持在原 ID 下续跑；补充信息或再次尝试须使用新 ID。

规范化仅包括主题去除首尾空白、预算转为固定精度金额、截止时间转为同一时间点、缺失字段转为统一空值，不做主题语义相似度判断。调试故障配置及模型模式属于首次执行配置，应记录；重复提交不能借这些选项隐式重跑原 ID。

任务记录须保存到本地，正常重启后仍能查询与识别重复请求。若发现遗留的 `running` 记录且已无执行进程，本期将其标为未完成并说明执行中断，不自动续跑，不猜测未确认的保存或计费结果。

## 7. 信息不足与输入错误

| 情况 | 状态与处理 |
| --- | --- |
| 主题、预算或截止时间缺失 | `needs_input`；列出所有缺失项，不调用模型及业务工具 |
| 金额为负、超过两位小数、时间无法解析等 | `needs_input`；指出具体字段及有效格式，不调用模型及业务工具 |
| 截止时间已到 | `incomplete`；原因为 `DEADLINE_EXCEEDED`，不执行业务工具 |
| 素材检索无结果或素材不可用 | 将真实结果交给模型，允许改检索条件；最终仍不足则 `incomplete` |
| 预算不足以执行下一必要工具 | 返回预算阻止观察；由模型选择其他有效动作或停止，最终不得虚报成功 |

不从主题猜测预算或截止时间，不为素材不足伪造素材。CLI 单次执行不等待交互补充，返回缺失项后结束；用户补全输入，以新任务再次提交。

## 8. 工具失败与计划调整

### 8.1 失败语义

工具错误至少包含 `error_code`、错误摘要、`retryable`、实际计费与耗时信息。没有结果和执行失败应区分记录：例如检索正常完成但没有素材，不等于工具崩溃。

- 可恢复错误示例：测试注入的一次性工具故障。模型可以重试或选择其他有效路径，是否重试由模型决定。
- 不可恢复错误示例：素材授权无效、指定方案不存在。模型可以选择其他合法素材或重新生成；不能原样反复提交无效对象。
- 模型接口不可用或响应无法被处理时，返回 `incomplete` 和具体错误，保留已有结果。本期不自动切换为 Mock 冒充真实模型执行。
- 保存失败仍是失败；只有后续保存工具实际成功才可完成任务。

业务工具执行器不自动重试。模型重新发出的调用作为新步骤、新费用和新耗时记录。参数错误与门禁拒绝也应反馈给模型，允许其纠正，但受统一决策上限约束。

### 8.2 保留结果与版本一致性

- 已成功步骤的结果与历史状态不可因后续失败而删除或改成失败。
- 每次实际工具调用是独立步骤，重试不覆盖之前的失败记录。
- 方案与脚本按版本记录；改写形成新版本，历史版本可以保留，但应明确哪个版本是当前候选、哪个已被替代。
- 成本估算绑定具体方案版本、费用规则版本和当时的工具费用。换方案后旧估算不能继续用于保存新方案。
- 保存必须使用可用素材、成功生成的脚本、当前版本的成功估算与最新账本；依赖不满足时阻止执行并记录原因。

## 9. 状态、上限与保存条件

### 9.1 任务与步骤状态

| 任务状态 | 含义 |
| --- | --- |
| `running` | 输入合法，任务正在执行 |
| `needs_input` | 输入缺失或格式错误，等待用户以新任务补充 |
| `succeeded` | 当前方案满足约束且已实际保存成功 |
| `incomplete` | 已结束，但未满足成功条件；必须有原因 |

步骤状态至少区分 `pending`、`running`、`succeeded`、`failed`、`blocked`、`skipped`。`blocked` 表示执行前被拒绝，`skipped` 表示计划调整后未执行；都不能记为工具成功。方案版本是否仍被采用，使用单独字段表示，不改写历史成功状态。

### 9.2 执行上限

- 每个任务最多 12 轮模型决策，每轮至多执行一个业务工具。
- 业务工具实际执行次数最多 12 次，失败执行也计数。
- 无效参数、未知工具、门禁拒绝、空动作等仍消耗一轮模型决策，防止无工具执行时无限循环。
- 第 12 轮若已保存成功，正常返回成功；否则返回 `incomplete`，原因为 `EXECUTION_LIMIT_REACHED`。不为生成结束文案额外开启第 13 轮。
- 模型主动结束但无保存成功结果，返回 `incomplete`，采用其与实际观察一致的原因；原因不明确时使用 `MODEL_STOPPED_WITHOUT_SAVED_PLAN`。
- 结束文案和最终状态由执行结果汇总，不接受模型自行修改账本或把失败步骤标为成功。

### 9.3 保存门禁

程序必须在调用保存前验证：当前方案及脚本有效、素材依赖有效、估算对应当前方案版本、最新预计总费用不超过预算、保存可按时完成。

门禁失败只返回结构化拒绝原因，由模型决定后续动作。保存成功后直接结束任务，不再执行收费工具。输出中的完成方案、估算与保存结果必须对应同一版本。

## 10. 验收场景与通过标准

以下均为待实现的测试规格，不代表已执行结果。测试只固定输入、素材、费用、时钟和工具故障等外部条件，不伪造模型动作或决策日志。模型可选择不同合法路径，以真实执行结果和业务不变量判定。

统一测试起点可设为 `2030-01-01T10:00:00+08:00`，预算单位均为模拟单位。

| 编号 | 输入与外部条件 | 预期结果及关键检查 |
| --- | --- | --- |
| A01 正常完成 | 主题“春季新品推广”，预算 20，截止 10:30；素材充足、工具正常，存在可行方案 | 核心四工具均有实际成功结果；账本正确；按时保存；最终 `succeeded` |
| A02 必要信息不足 | A02a 缺预算；A02b 缺截止时间；其余字段合法 | 均为 `needs_input`，明确缺失项；无模型及业务工具调用、费用为 0、无保存结果 |
| A03 工具失败 | 沿用 A01 的宽裕约束，在首次脚本生成时注入一次可恢复错误 | 若触发故障，模型随后选择重试、有效替代路径或明确停止；检索成功结果保留；失败脚本不标成功；失败费用和耗时均累计 |
| A04 超预算后调整成功 | 预算 10，截止 10:30；使用可触发超限且存在更低价替代的合成材料与费用配置 | 必须实际出现一次总费用超预算的成功估算；模型观察后修改候选方案并重新估算；最终总费用不超过 10 并实际保存；历史费用不清零 |
| A05 无可行预算 | 预算 3，截止 10:30；按默认费用表，最短核心链路仅工具费用就需 4 | `incomplete`，无成功保存；说明预算不足。若尚未取得有效方案估算，报告“工具费用下界缺口至少 1”，不得虚构精确总缺口 |
| A06 重复执行 | 对 A01 成功任务用相同 ID、相同输入再提交；另测相同 ID 修改预算，以及新 ID 使用相同输入 | 同 ID 同输入返回原结果，调用数、费用、保存数量均不增加；同 ID 改输入返回冲突；新 ID 作为独立任务执行 |
| A07 时间不足 | 预算 20，截止 10:08；默认完整核心链路至少需要 9 分钟 | `incomplete`，原因包含时间不足，无成功保存；说明最短链路至少超时 1 分钟，不允许靠跳过必要工具宣称完成 |
| A08 素材不足 | 合法输入，检索数据对该主题始终无可用素材 | 模型可调整检索条件或结束；最终未找到素材时为 `incomplete`；无虚构素材、脚本依赖或成功保存 |
| A09 执行上限 | 测试模型持续选择重复检索等有效但不能完成任务的动作；提供足够预算和时间 | 最多 12 轮决策及 12 次工具执行；未保存则 `incomplete`，原因 `EXECUTION_LIMIT_REACHED`；保留全部已执行记录 |
| A10 版本与边界 | 使用确定性测试分别覆盖估算后改写、估算后增加工具费用、保存失败、截止时刻恰好完成、保存前预算恰好用尽 | 旧版本估算不能保存新版本；门禁采用最新账本；保存失败不成功；等于截止时间与预算允许完成 |

A03 必须实际触发注入错误，A04 必须实际触发超预算观察；未触发时只说明该次运行未覆盖目标场景，不能当作该场景通过。用于触发场景的合成配置须事先定义并随证据归档，不能看完结果再修改日志。A03 若模型选择明确停止，仍可符合题目；另有正常场景验证完整成功链路。

A09 可使用明确标注的离线测试模型验证执行上限，不作为真实模型决策能力证据。A10 等确定性约束可由工具级和执行器级测试验证，无需把所有边界都交给真实模型重复运行。

## 11. Trace、证据与评估边界

### 11.1 Trace 最低字段

- 任务 ID、运行 ID、输入、`real` 或 `mock` 模式、模型标识、配置版本和测试时钟配置。
- 决策轮次、当前计划及步骤依赖、模型选择的动作与简短理由；不得要求或归档模型内部思维过程。
- 工具名称、调用 ID、实际参数、实际结果或错误、步骤状态。
- 本次费用与耗时、累计账本与模拟时间、方案及估算版本。
- 下一轮动作或终止原因，使观察与后续动作的关系可检查。
- 保存成功时的方案 ID 与路径；最终状态和缺口。

Trace 是实际运行事件记录，不得使用预写决策日志替代。密钥不得进入参数、Trace 或示例输出。

### 11.2 最低提交证据

至少归档三组输入、实际输出和 Trace，覆盖正常、信息或资料不足、工具失败；全部验收点仍需有对应证据，可使用更多独立用例。

至少保留两条来自真实模型的不同执行路径，建议为正常路径与超预算调整路径，以观察差异及后续动作证明模型会调整。工具失败路径也应有真实模型观察错误后选择继续或停止的记录。

证据放在 `examples/`，每个场景建议独立目录，包含输入、使用的场景配置、输出和 Trace；另存测试结果。`docs/03-evaluation.md` 应引用具体文件，列出预期、实际结果及通过情况。

离线 Mock 只验证工具、状态、费用、依赖、幂等和上限等工程行为。真实模型不可用时仍可交付 Mock 入口，但真实模型决策相关项目必须标为“未验证”，不能用 Mock 通过结果替代。调用真实模型产生的输出也不能自动视为通过，应逐项核对验收标准。
