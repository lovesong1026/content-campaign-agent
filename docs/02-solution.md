# 内容任务规划 Agent：开发方案 v1

状态：v1 技术设计已有对应实现；实际结果与验证边界见 [评估报告](03-evaluation.md)。业务约束以 [需求与验收约定](01-requirements.md) 为准，交付清单见 [README](../README.md)。

## 1. 实现目标与职责边界

通过 CLI 输入主题、预算和截止时间，生成并保存一份短视频活动方案。真实模式使用 DeepSeek Flash 选择下一步动作，观察本地工具的实际返回值，在超预算或失败后重新选择动作。

首版同时支持单任务和批量任务；独立任务可以并发，同一任务内部按依赖顺序执行。脚本生成工具也调用 DeepSeek，但不创建第二个 Agent。

| 模块 | 负责 | 决策边界 |
| --- | --- | --- |
| 规划模型 | 选择工具及参数、提出计划调整、决定是否停止 | 不能直接修改状态、价格、账本或保存结果 |
| 脚本生成模型 | 根据指定素材、数量及制作规格生成脚本 | 不选择下一业务动作，不执行工具，不决定预算是否合规 |
| Agent 循环 | 组织模型上下文，回传观察，执行轮次控制 | 不通过固定分支替模型挑选替代方案 |
| 工具执行器 | 校验参数、依赖、预算与时间，执行并记录结果 | 可以阻止无效动作，但不自动重试或降低方案规格 |
| 本地存储 | 保存任务快照、方案版本、调用结果与 Trace | 不将文件存在直接等同于任务成功 |

模型输入必须包含当前预算与时间余量，但程序独立执行全部门禁。运行成功必须对应一次实际成功的保存调用。

核心接口约定：

```text
ModelClient.decide(context, messages, record) -> await Decision
ModelClient.generate_script(request, record) -> await ScriptDraft
Agent.run_task(raw_input) -> await RunResult
Agent.resume_task(task_id) -> await RunResult
Agent.run_batch(raw_inputs) -> await BatchResult
Executor.execute(state, call) -> await ToolObservation
Storage.load(task_id) -> await TaskState | None
Storage.save(state) -> await None
```

场景在 Agent 构造时指定；record 为异步事件记录回调。任务快照和方案使用可序列化字典，工具参数、脚本及场景采用 Pydantic 校验。模型适配层只处理请求、响应和用量，不记业务费用。执行器只接收经过解析的动作，不读取模型密钥。存储路径由程序生成，模型不能指定任意文件路径。

## 4. 数据契约与最终方案

### 4.1 输入与金额表示

业务输入继续使用 `theme`、`budget`、`deadline` 和可选的 `task_id`。CLI 保留原始输入，统一校验后产生 `needs_input` 等结构化结果，不能因参数解析异常丢失缺失项说明。

- 预算通过字符串或精确十进制解析，不能先转为二进制浮点数。
- 费用内部使用 `Decimal`，JSON 中统一写为两位小数字符串，如 `"8.00"`。
- 时间解析为带时区的时间点；缺省时区按北京时间解释，内部统一比较时间点。
- 未估算的费用为 `null`，不以 `"0.00"` 替代未知。
- 未提供任务 ID 时生成 UUID；目录名使用任务 ID 的 SHA-256，避免将用户输入直接拼入路径。

### 4.2 核心对象

| 对象 | 关键字段与不变量 |
| --- | --- |
| `TaskState` | task_id、run_id、input_fingerprint、status、phase、started_at、decision_rounds、tool_calls、current_plan_ref、ledger、events |
| `Material` | asset_id、title、tags、description、facts、license、available；合成数据不冒充真实商业授权 |
| `CampaignPlan` | plan_id、version、theme、audience、channel、items、content_hash；费用不由此对象自行声明 |
| `VideoItem` | video_id、title、asset_ids、production_tier、hook、body、cta、shots |
| `CostEstimate` | estimate_id、plan_ref、content_hash、pricing_version、breakdown、plan_cost、tool_cost_at_estimate、total_at_estimate |
| `LedgerEntry` | call_id、tool_name、fee、duration_seconds、outcome；同一实际调用只记一次 |
| `ToolObservation` | call_id、status、data 或 error、本次及累计费用、模拟时间、requires_replan |
| `TraceEvent` | event_id、顺序号、round、call_id、事件类型、参数或结果引用、费用与状态摘要 |

`plan_ref` 为任务内的方案 ID 与版本组合，不能跨任务读取。内容变更形成新版本，旧脚本、旧估算和旧步骤状态持续保留。估算绑定内容哈希与费用规则版本，当前方案的价格规则在一次任务内固定。

### 4.3 短视频范围与质量判断

首版方案支持 1 至 3 条短视频，默认单一发布渠道。每条视频均有真实检索得到的素材引用、制作规格、开场、正文、行动提示及镜头建议。视频时长属于内容属性，不等于业务工具的模拟耗时。

自动检查字段完整、素材可用、引用有效、版本匹配及费用一致；主题契合度、脚本可读性、事实是否受素材支持需要在评估时人工检查并记录。不能用结构校验通过替代内容质量验证。

## 5. 四个业务工具

### 5.1 通用调用与错误结构

每个工具参数包含必填 `decision_note`，仅要求与当前观察有关的一句话行动理由，不索取内部思维过程；可附带 `remaining_steps`，表示模型建议的后续工具序列。执行器将这两个字段作为计划元数据记录，再传递实际业务参数。

轻量 TodoList 已接入决策循环：`remaining_steps` 省略或 null 时保留后续待办，显式空数组才清空；执行器维护稳定 ID、真实状态与修订快照。每轮上下文包含当前待办及修订摘要，旧快照不伪造回填。实现及验证见 [TodoList](07-todolist.md)。

初始计划可展示检索、生成、估算、保存四个待执行目标。后续计划快照来自模型提供的行动建议和实际调用；每次执行关联独立步骤，替代版本明确标记。模型只建议计划，步骤的实际状态由程序更新；结束时未执行的计划步骤为 `skipped`。

工具结果统一包含：

```json
{
  "call_id": "call_example",
  "status": "failed",
  "data": null,
  "error": {
    "code": "INJECTED_TOOL_FAILURE",
    "message": "本次脚本生成遇到一次性故障",
    "retryable": true
  },
  "fee": "2.00",
  "duration_seconds": 300,
  "cumulative_tool_cost": "3.00",
  "requires_replan": true
}
```

该 JSON 是接口示例，不是运行证据。参数或依赖校验失败使用 `blocked`，费用和耗时为 0。业务函数已经开始执行后出错使用 `failed`，按费用表收费并累计耗时。`retryable` 表示允许模型考虑重试，不触发程序自动重试。

### 5.2 工具接口

| 工具名 | 业务输入 | 返回内容 | 依赖与失败规则 |
| --- | --- | --- | --- |
| `search_materials` | query、可选素材类型过滤 | search_result_id、素材列表及事实说明 | 从本地材料做确定性筛选；空列表是成功检索但资料不足，触发重新决策 |
| `generate_script` | audience、channel、items，单项指定 asset_ids、production_tier、内容要求；可选 base_plan_ref | 新的完整方案版本与脚本 | 素材必须在本任务已成功检索结果中且可用；调用 DeepSeek，结果必须通过结构及引用校验 |
| `estimate_cost` | plan_ref | 价格明细、方案预计费用、当前工具费用、总费用及可行性信息 | 方案必须已生成成功；基于固定费用规则计算，不能接受模型自报金额作为依据 |
| `save_plan` | plan_ref、estimate_id | saved_plan_id、相对路径、内容哈希、保存时最终费用 | 当前版本有成功估算、依赖有效、最新总费用合规且能按时保存，才可真正执行 |

模型不能修改素材授权、费用规则或工具耗时。生成工具产出的素材 ID、制作规格和视频条数必须与其输入相符；生成模型擅自换素材或加条目时，本次工具失败，交回规划模型处理。

### 5.3 成本规则与示例数据

工具费用与耗时沿用需求文档：检索 1 单位 / 2 分钟、生成 2 / 5、估算 1 / 1、保存 0 / 1。

初始合成价格可按下表固化，所有价格非负：

| 项目 | 价格 | 计费粒度 |
| --- | ---: | --- |
| 基础素材 | 0.00 | 同一方案每个独立素材 ID 一次 |
| 高级素材 | 3.00 | 同一方案每个独立素材 ID 一次 |
| economy 制作 | 1.00 | 每条视频 |
| standard 制作 | 2.00 | 每条视频 |
| premium 制作 | 5.00 | 每条视频 |

首版渠道发布预计费用为 0，规则中显式记录。方案费用 `P` 为去重后的素材费用加每条视频制作费用及发布费用；总费用为累计工具费用 `C + P`。这是模拟内容执行价格，保存时不实际执行拍摄或发布。

预算为 10 时，一条高级素材加 premium 视频的 `P=8`；首次检索、生成、估算后 `C=4`，总计 12。若模型随后改为一条基础素材加 economy 视频，再生成并估算后 `C=7、P=1`，总计 8。该例用于验证价格口径；实际模型也可能直接选便宜方案，不能据此声称观察到了超预算调整。

估算工具在计算返回值前计入本次估算费用。保存前使用最新 `C` 加当前有效估算的 `P`，不能盲用估算时的旧总价。候选方案更换只替换 `P`，不清空 `C`。

## 6. DeepSeek 接入与提示设计

### 6.1 固定接入选择

- 基础地址：`https://api.deepseek.com`。
- 模型：`deepseek-flash`。
- 客户端：共享一个 `AsyncOpenAI`，由 CLI 生命周期统一创建与关闭。
- 接口：`client.chat.completions.create`，使用 `await`。
- 两类请求都显式传入 `extra_body={"thinking": {"type": "disabled"}}`。
- 首版不使用流式输出；一次完整响应校验后再分发工具。
- 模型请求设置总等待上限 60 秒，SDK 自动重试设为 0；重试策略不会隐藏在客户端内部。
- 规划输出上限初值为 2048 tokens，脚本输出初值为 4096 tokens；实际适配及用量在运行后验证。

DeepSeek 的工具调用由应用执行并回传，参见 [官方工具文档](https://api-docs.deepseek.com/guides/tool_calls/)。官方默认开启思考模式；本方案显式关闭以简化首版协议处理，参见 [思考模式说明](https://api-docs.deepseek.com/guides/thinking_mode/)。

不假设 `parallel_tool_calls=False` 能约束 DeepSeek Chat Completions 的返回数量；应用按实际 `tool_calls` 数组处理。多调用控制与业务并发由本项目执行器承担，参见 [Chat Completions 接口](https://api-docs.deepseek.com/api/create-chat-completion/)。

### 6.2 规划请求

规划请求携带四个函数工具的 JSON Schema，允许模型选择工具或结束；不强制固定的下一个函数。工具参数本地再用 Pydantic 验证，首版不依赖 Beta strict 模式。

规划上下文按固定区块组织：角色与目标、用户输入、可信业务规则、当前方案及计划、成功结果引用、最新观察、费用与时间、剩余额度。

提示应明确：

1. 为运营人员制定短视频方案，根据真实观察选择动作。
2. 已发生费用持续累计；替代方案也有工具费用。
3. 素材或方案 ID 只能引用当前任务已有结果，不能预测尚未产生的 ID。
4. 超预算或失败后可以修改、重试、换路径或停止，但只能通过实际工具取得结果。
5. 同一响应内的调用不会并行执行；遇到需重新决策的观察时，剩余调用会被跳过。
6. 只给简短行动理由，不输出内部思维过程；结束说明不能代替保存。

素材与错误描述作为数据区块输入，不作为系统指令。账本、时间和状态来自执行器，不能由模型覆盖。后续调用保留完整的任务内协议历史，并追加最新可信状态摘要；批量任务之间不共享 messages。

### 6.3 脚本生成请求

使用独立提示和独立 messages，输入主题、指定素材事实、受众、渠道及制作规格，不携带业务工具列表。模型只输出约定的脚本 JSON，使用 `response_format={"type":"json_object"}`；提示包含 `json` 字样及结构示例。

JSON 模式不代替字段、引用和语义边界校验；空内容、截断、JSON 解析失败或引用无效均作为脚本工具失败。此类失败返回规划模型，由其决定是否再次调用，生成工具内部不自动修复重试。参见 [DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。

规划与脚本提示分别记录版本及内容哈希。真实模型返回的 model 字段、请求 ID（若可用）、token 用量和实际 SDK 版本进入运行元数据。`deepseek-flash` 是服务标识，不能声称它保证后端模型永远不变。

## 7. Agent 执行流程与多调用处理

以下为流程伪代码，不是可直接运行的实现：

```text
校验输入、查重并取得本任务执行权
记录配置与材料版本，取得任务并发名额，设置 started_at
检查截止时间是否已到

while 尚未成功且 decision_rounds < 12 且 tool_calls < 12:
    decision_rounds += 1
    调用规划模型，记录请求及用量
    校验响应、调用 ID 与工具参数

    if 没有工具调用:
        将模型的停止说明与真实状态核对，返回未完成

    保存 assistant 消息及全部原始 tool_call_id
    按返回顺序处理各调用:
        若前项触发重新决策、上限或保存成功:
            记录 skipped，不收费、不累计耗时
        否则:
            校验名称、参数、依赖、费用、时间及保存门禁
            被拒绝则记录 blocked
            允许执行则分配 call_id、记账、累计模拟耗时并执行
            保存真实结果及状态
        为每个原始 tool_call_id 形成一条 tool 观察

    若保存成功，立即结束任务
    若触及任一上限，返回未完成
    否则将全部 tool 观察回传，进入下一轮

汇总实际状态、费用、保存结果与原因；导出 Trace
```

### 7.1 观察边界

工具失败、门禁拒绝、检索素材不足或成功估算显示超限时，`requires_replan=true`，本批后续调用为 `skipped`，原因为 `REPLAN_REQUIRED`。停止继续执行只是把观察交回模型，不替模型选择下一条路径。

同一响应不能依赖尚未返回的新方案 ID。已知对象上的多个调用可以串行处理，每项都读取更新后的账本和时钟，不能在批次开始时一次性放行全部调用。

一批最多接受 12 个原始调用；超过时整批阻止执行并反馈数量限制，消耗一轮决策。重复或缺失 tool call ID 属于协议错误，结束为未完成，不猜测配对关系。对已接受的合法调用 ID，成功、失败、阻止或跳过均有明确结果记录；继续请求模型前必须补齐全部 tool 消息。

### 7.2 上限、失败与终止

- 一次规划模型请求算一轮；脚本工具内部请求单独统计，不占新的决策轮次。
- 实际执行的工具才消耗工具调用额度，包括失败；参数错误和门禁拒绝不消耗工具额度，但所在轮次照常计数。
- 第 12 轮或第 12 次工具执行若保存成功，返回成功；否则返回 `EXECUTION_LIMIT_REACHED`。
- 保存成功后该批剩余调用全部跳过，不能继续增加费用。
- 规划接口连接失败、认证失败、超时或响应截断导致无法处理，返回相应模型错误及未完成状态；不自动切换 Mock。
- 脚本生成请求失败属于业务工具失败，按生成工具费用和耗时记账，允许规划模型重新决策。
- 用户取消时尽力落盘为 `incomplete / CANCELLED`；强制终止进程时以最后已持久化记录为准。

## 8. 异步、并发与幂等

### 8.1 两种并发限制

`run_batch` 使用任务信号量，默认同时执行 3 个独立任务；模型适配层使用另一个请求信号量，默认最多 3 个正在进行的模型请求。两者是不同对象，避免嵌套获取同一信号量导致死锁。

- 单个任务等待模型时让出事件循环，同一任务的业务工具仍串行执行。
- 某个任务的失败转换为该任务的结果，不取消其他任务；批量结果按输入顺序汇总。
- 用户取消整个批次时取消子任务，各自尝试记录已完成结果。
- 模拟工具耗时只累加数值，不调用 sleep 等待几分钟。
- 文件读写按需使用 `asyncio.to_thread`，金额计算和小型参数校验保持同步。

### 8.2 重复任务与等待队列

按规范化业务输入生成指纹。提交时在任务 ID 对应的短临界区内完成“查找、比较、登记”，随后释放锁；不能持锁等待整次模型执行。

- 同 ID 同输入：已有任务执行中时返回当前快照，结束后返回原结果，不再进入任务队列。
- 同 ID 不同输入：返回 `TASK_INPUT_CONFLICT`，不覆盖记录。
- 新 ID：独立登记、执行、计费和保存。
- 等待任务名额时使用 `running` 状态及 `phase=queued`；真正取得名额后记录 `started_at`。
- 队列等待会使实际启动时间变晚；取得名额后重新比较截止时间，不能使用入队时的旧时间点。

批量最终汇总时，同 ID 同输入的复用项读取该批原执行的最终快照，避免原执行已完成但复用项仍显示入队时的状态；同 ID 不同输入的冲突项保留冲突错误，不能被最终快照覆盖。

首版只允许一个写入进程使用同一个输出目录；macOS / Linux 使用标准库 `fcntl.flock` 持有目录级运行锁，第二个写入进程明确报占用。`show` 可读取原子快照。该锁由操作系统在进程退出时释放，不需要猜测残留 PID；任务 ID 的 `asyncio.Lock` 负责同一进程内的重复请求。

取得目录写锁后，启动时发现遗留 `running` 记录，将其标为执行中断，不自动续跑；保留已经确认的调用与费用，对未确认的调用结果标明未知，不编造成功。

显式 `resume` 在同一任务 ID 的短临界区内登记新一轮续跑，再进入原任务信号量和模型循环。原输入、`run_id`、费用与耗时、调用序号及累计上限不变，业务工具使用原快照规则；首轮模型上下文包含历史真实步骤，不重放未闭合的工具调用会话。TodoList 追加新待办与 `TASK_RESUMED` 修订，不重新打开历史失败。成功或正在执行的任务只返回已有状态；并发续跑只启动一次。

## 9. 时间、费用和存储的一致性

### 9.1 执行前后顺序

每项调用遵循：校验参数与依赖 → 校验费用和时间 → 登记执行开始及费用、耗时 → 执行业务函数 → 保存成功或失败结果 → 更新任务快照。

登记执行开始是模拟工具计费的边界；通过门禁且进入执行的调用按完整费用和耗时记账。业务函数失败不回滚账本。原始供应商 API 的实际账单、是否被服务端处理，在网络超时下可能未知，应单列而非混入模拟账本。

估算的剩余时间应覆盖尚未完成的必要步骤，包括保存。保存门禁以当前模拟时间加保存耗时检查，恰好等于截止时间允许执行。独立任务的并发不改变各自的模拟时间公式。

### 9.2 存储布局与可信来源

```text
.runs/
  .writer.lock
  tasks/<task-id-hash>/
    task.json              # 权威任务快照，含费用账本和有序事件
    trace.jsonl            # 从已持久化事件导出的 Trace
    results/<call-id>.json # 完整工具结果
    plans/<id>-v<n>.json   # 不可覆盖的方案内容版本
    saved/<saved-id>.json  # 保存工具产出的交付方案
```

JSON 文件写入同目录临时文件，刷新后以 `os.replace` 原子替换；按任务串行提交，避免两个异步写入相互覆盖。`task.json` 内的账本与状态一起更新，不能分别写两个互相矛盾的权威文件。

Trace 使用任务快照中的事件列表生成，允许重新导出，以 event_id 去重。少量事件可整体原子重写 JSONL，避免将追加日志误当成跨文件事务。完整工具观察先与实际步骤、账本一同写入权威任务快照，再导出 `results/` 文件，避免结果文件先落盘而快照仍把成功调用视为未知。方案文件及交付文件仍须写入成功，才能确认对应调用成功。

本方案不承诺多个文件的数据库级原子事务。若交付文件已写但任务状态尚未确认就中断，重启后保留文件并报告未完成，不凭文件存在推断原任务已经成功，也不自动重跑保存。显式续跑时先核对交付文件的完整内容与原快照，一致则确认原保存调用、追加 `save_reconciled` 事件；不一致或损坏返回 `SAVED_RESULT_CONFLICT` 且不覆盖。只有文件不存在时才允许模型发起新的保存尝试。其他未知结果的工具尝试仍保留原收费，新尝试再次收费。

## 10. CLI 与配置约定

以下命令已有实现，先按 README 安装环境：

```bash
uv sync --locked
uv run python -m content_campaign_agent run --input examples/inputs/normal.json
uv run python -m content_campaign_agent batch --input examples/inputs/batch.json --concurrency 3
uv run python -m content_campaign_agent show --task-id demo-normal
uv run python -m content_campaign_agent resume --task-id your-task-id
uv run python -m content_campaign_agent run --input examples/inputs/normal.json --mode mock
uv run pytest
uv run ruff check .
uv run ruff format --check .
```

`run` 输入为一个 JSON 对象，`batch` 为对象数组；也应支持 `run --theme ... --budget ... --deadline ...` 直接传参。两种输入方式互斥，业务缺失项交给统一校验。`show` 只查询，不发起模型请求。`resume --task-id ...` 读取原任务，不接收新的业务输入或场景，`--mode` 必须与原任务一致。缺输入或模式不符时退出码为 2，原状态保留。

输出的 `gaps.minimum_total_cost` 与 `gaps.minimum_total_budget_gap` 展示总费用下界及最低缺口，复用模型上下文的同一计算逻辑。尚未实际估算时，`costs` 中的方案费用、总费用及精确缺口继续保持 `null`。

单任务成功退出码为 0，未完成为 1，输入错误或任务输入冲突为 2；批量全部成功为 0，任一任务未成功为 1，批量输入文件本身不可解析为 2。一次性命令的 stdout 输出 JSON 结果，诊断日志输出 stderr。

`interactive` 或不带子命令的启动进入交互会话；模式、目录和场景参数放在 `interactive` 后。会话在同一个 `asyncio.Runner` 中复用 Agent 及模型连接，终端输入发生在异步任务执行之外，避免输入等待阻塞取消收尾。业务输入复用统一校验，非法值只重填对应字段；截止时间可显式接受界面展示的 30 分钟默认值。会话持有原目录写锁，每个新主题创建新任务，`resume` 转入原续跑入口。

执行器在权威事件持久化后调用可选进度回调，仅展示实际轮次、工具开始及结果，不伪造完成状态，也不把展示异常当成业务失败。人类可读结果包含费用、缺口、真实历史步骤和保存位置；一次性 JSON 协议不变。正常退出或 EOF 返回 0，配置缺失返回 2，Ctrl+C 取消并收尾后返回 130。所有退出路径统一调用 `Agent.close()` 关闭模型并刷新遥测。

配置初始化时读取现有 `.env` 的三个字段：`DEEPSEEK_API_KEY`、`DEEPSEEK_BASE_URL`、`DEEPSEEK_MODEL`。先完成业务输入校验；缺预算或截止时间时直接返回 `needs_input`，不因尚未配置密钥而掩盖缺失项。合法任务在首次模型请求前检查真实模式的密钥是否可用。后续可在 Settings 中增加以下默认值并同步 `.env.example`：

| 配置 | 默认值 |
| --- | --- |
| `MODEL_TIMEOUT_SECONDS` | 60 |
| `MAX_CONCURRENT_TASKS` | 3 |
| `MAX_CONCURRENT_MODEL_REQUESTS` | 3 |
| `OUTPUT_DIR` | `.runs` |

决策轮次和工具调用上限首版固定为 12。真实模式缺密钥时报告配置错误；Mock 模式不要求密钥且不访问网络。密钥使用敏感配置类型，日志和配置快照采用字段白名单，禁止记录请求认证头。现有 `.env` 保持本地且由 Git 忽略。

## 11. 测试、故障注入与证据

### 11.1 验证分层

| 层次 | 验证内容 | 是否需要真实模型 |
| --- | --- | --- |
| 工具测试 | 检索、素材有效性、价格明细、脚本结构及保存结果 | 本地工具不需要；生成工具可注入受控客户端 |
| 执行器测试 | 计费、时间、版本、门禁、失败保留、多调用、上限 | 不需要 |
| Agent 测试 | 消息配对、真实观察回传、终止与 Mock 边界 | 可先使用测试客户端验证工程行为 |
| 并发测试 | 并发上限、同 ID 只执行一次、任务隔离、单任务失败不取消其他任务 | 不需要，用异步事件控制时序 |
| 真实模型验收 | 正常、工具失败、超预算后的模型后续选择及内容质量 | 必须需要 |

测试对应需求文档 A01—A12。新增多调用测试必须覆盖：一轮返回多个调用、前项失败后的跳过、逐项重新检查费用、达到上限、保存后不再执行。并发测试检查实际进行中的任务数和模型请求数，不依赖易抖动的总耗时断言。

### 11.2 外部条件与故障注入

测试场景通过显式配置选择素材、费用规则、固定时钟以及“指定工具第 N 次实际执行失败”。故障只改变工具返回或外部数据，不控制下一次模型动作。一次性故障标记按任务及场景保存，重复读取任务不重新注入。

真实模型超预算场景使用事先定义的高规格偏好和可替代材料，保留原始输入与完整规则。模型可能直接选低成本方案；这种运行可以证明可行性，但不能算 A04 通过。只有实际超预算估算之后，出现新的模型响应并调整方案，才记录为重规划证据。失败路径同理，预先排在同一响应里的动作不能证明模型观察后改变了决定。

离线 Mock 可以按受控策略生成动作，用于稳定测试状态机与消息协议；所有记录标记 `mode=mock`，不与真实模型通过结论混用。

### 11.3 证据归档

至少归档正常、缺信息或资料不足、工具失败三类输入及结果，并以额外场景覆盖超预算、重复执行等验收点。真实模型至少保留正常与观察后调整两条不同路径，并提供工具失败后的实际模型选择。

每个证据目录包含输入、场景配置快照、实际输出、Trace、被引用的方案和工具结果。复制到 `examples/` 时使用可移植的相对路径；不能只留下指向本机 `.runs/` 的链接。

Trace 记录规划及脚本请求的角色、模型标识、提示版本、用量和请求状态；工具事件记录实际参数、结果摘要或文件引用、前后费用、时间及状态。决策依据只记录简短行动理由，不导出内部思维字段。真实 API 费用若无法取得则显示未知，不按模拟工具费用冒充真实账单。

`docs/03-evaluation.md` 在实际运行后填写预期与实际差异、证据路径、通过或失败及限制。AI 使用记录和复盘同样依据真实开发过程填写，不提前写成已完成。

## 12. 实施顺序与阶段完成标准

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| M1 基础工程 | uv 项目、Settings、数据对象、合成素材及费用表 | 配置可校验，Mock 不需密钥，金额与时间可确定性计算 |
| M2 工具与存储 | 四工具接口、方案版本、任务快照、账本、原子保存 | 工具测试及保存门禁测试通过，失败结果可追溯 |
| M3 真实闭环 | 异步客户端、两类提示、规划循环、多调用处理 | 正常路径使用真实模型完成保存，Trace 对应实际执行 |
| M4 调整与并发 | 超预算调整、工具故障、批量限流、同 ID 幂等 | 有模型观察后调整证据，并发及幂等测试通过 |
| M5 交付核验 | 全验收、证据归档、README、评估、AI 使用、复盘 | A01—A12 对应证据与测试可检查，真实与 Mock 结论分开 |

优先实现可运行核心链路，每阶段记录实际用时和未完成项。若投入时间用尽，明确标记尚未完成的阶段和验收点，不能将设计文档、Mock 路径或计划中的命令当作真实运行证明。
