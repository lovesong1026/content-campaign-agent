# 小影科技校招 AI Agent 开发考核：内容任务规划 Agent

本文件用于明确开发范围、验收标准与交付要求。当前是任务说明，不代表项目已经实现或通过验证。

## 1. 要解决的问题

帮助运营人员在给定预算与截止时间内，完成一份内容活动方案。

系统需要根据工具返回的真实执行结果推进任务：当成本超限、工具出错或只有部分步骤成功时，由模型决定调整计划、选择替代方案或停止，并保留已经成功的结果。

考核重点是业务理解、模型决策、工程实现、效果验证，以及学习和改进能力。允许使用 AI 辅助开发，但必须如实记录使用范围、个人贡献和验证结果。

## 2. 输入、工具与输出

### 输入与材料

| 类型 | 内容 |
| --- | --- |
| 用户输入 | 活动主题、预算、截止时间 |
| 项目提供的材料 | 合成素材、工具费用表、工具耗时表 |

### 必须提供的业务工具

| 工具 | 职责 |
| --- | --- |
| 素材检索 | 查找可用于活动的素材 |
| 脚本生成 | 生成内容脚本 |
| 成本估算 | 根据方案与费用规则计算成本 |
| 方案保存 | 保存最终方案并返回保存结果 |

业务工具可以使用本地函数或 Mock，无须接入真实外部业务服务。

### 交付结果

每次任务执行应能查看：

- 任务计划与各步骤状态。
- 已执行工具的结果。
- 费用合计。
- 已保存的方案；如果没有完成，则说明未完成原因。

## 3. Agent 决策的最低要求

必须至少实现一个完整的模型决策循环：

```text
用户目标与约束
      ↓
模型选择下一步动作
      ↓
执行工具并返回结果
      ↓
模型观察结果
      ↓
调整下一步动作，或结束任务
```

可以用预设流程作为执行骨架，但关键调整必须由模型根据观察结果决定。仅有固定条件分支、自动重试或预先编写的决策日志，不满足题目要求。

### 参考路径：超预算后重新规划

```text
预算：10 个模拟单位
初始方案 → 成本估算为 12
模型观察到超预算 → 选择替代方案
替代方案 → 再次估算为 8
满足约束 → 保存方案 → 返回完成结果
```

如果没有可行方案，应返回未完成及缺口，不能为了结束任务而把失败步骤标为成功。

### 状态与终止要求

- 调整计划或处理失败时，保留已成功步骤的结果。
- 步骤依赖、实际执行结果和记录状态应一致。
- 必须设置执行步数或工具调用次数上限。
- 达到上限仍未完成时，明确返回未完成状态。
- **失败步骤续跑属于加分项**，不属于最低完成要求。

## 4. 验收场景

以下五项都必须覆盖。表中检查重点是对原题要求的整理；具体交互方式需要在项目需求文档中定义。

| 必须验收的场景 | 检查重点 |
| --- | --- |
| 正常完成 | 完成核心工具链路，费用计算正确，方案成功保存 |
| 缺预算或截止时间 | 识别必要信息不足，明确说明缺失项与当前状态 |
| 工具失败 | 注入一次工具失败，观察模型是否调整计划或明确停止，并保留已成功结果 |
| 预算超限 | 模型根据成本估算结果选择替代方案；无可行方案时返回未完成及缺口 |
| 重复执行 | 明确定义重复执行行为，检查状态、保存结果与费用记录是否符合定义 |

截止时间是业务约束，需要结合耗时材料参与可行性判断。原题没有规定具体时间计算方式，项目应说明采用的规则与边界。

## 5. 测试与运行证据

### 数量与覆盖要求

- 至少提交 **3 组输入、实际输出和运行记录**，覆盖正常、信息或资料不足、工具失败三类场景。
- 这些用例还必须覆盖第 4 节的全部验收点；同一用例可以覆盖多个验收点。
- 至少提供 **两条执行路径**的运行记录，体现模型根据不同工具结果调整动作。
- 提供可执行测试，Trace 和测试结果存放在 `examples/`，评估文档引用对应文件。

三组用例是最低数量，不代表只验证三个验收点。可以增加独立用例，让失败原因和模型调整行为更容易检查。

### 每条 Trace 应包含

| 字段 | 内容 |
| --- | --- |
| 执行步骤 | 步骤顺序及对应动作 |
| 工具参数 | 实际传入的参数 |
| 返回摘要 | 工具返回的关键结果或错误 |
| 后续动作 | 模型接下来选择执行什么，或为何结束 |
| 简要决策依据 | 与观察结果相关的简短说明 |

无须提交模型内部思维过程。运行记录必须对应实际执行，不能用预设日志替代真实模型决策证据。

### 真实模型与离线 Mock 的边界

模型不可用时，需要提供离线 Mock 入口，并明确说明其能力边界：

- 离线 Mock 可以验证流程、工具调用和状态处理。
- 离线 Mock **不能证明真实模型的决策效果**。
- 评估文档应区分真实模型运行结果与 Mock 运行结果，不能混用结论。

## 6. 技术范围与投入建议

| 项目 | 题目要求 |
| --- | --- |
| 建议投入 | 3 小时；优先完成核心链路，记录实际用时和未完成部分 |
| 语言、模型、框架 | 自选；可原生实现，也可使用 Google ADK、AgentScope、LangGraph 等 |
| 运行入口 | CLI、HTTP API、Notebook 三选一 |
| 可复现性 | 必须提供可复制的运行命令或执行步骤；截图、视频不能替代代码 |
| 非必需内容 | 界面、线上部署、多 Agent、生产级 Runtime |
| 框架说明 | 使用框架时注明版本、使用的功能及职责，无须重新实现框架本身 |

框架名称本身不加分，能解释取舍、修改和验证结果才有价值。

**建议的最小实现路线（不是题目强制技术方案）：** 采用 CLI、单 Agent、真实模型和四个本地业务工具，先打通“执行—观察—调整”的闭环，再补齐状态处理、验收用例和文档。

## 7. 仓库交付结构

目录可以按技术栈调整，但必须包含对应的代码、文档和验证材料。

```text
.
├── README.md                 # 环境、安装、运行、评审入口
├── src/                      # 项目代码、模型与工具接入
├── tests/                    # 可执行测试
├── examples/                 # 输入、实际输出、Trace、测试结果
├── data/                     # 按题目需要提供合成素材、费用与耗时规则
├── docs/
│   ├── 01-requirements.md     # 用户、目标、范围、成功标准
│   ├── 02-solution.md         # 调用流程、动态决策、技术取舍
│   ├── 03-evaluation.md       # 测试预期、实际结果、失败与限制
│   ├── 04-ai-usage.md         # AI 辅助内容、个人修改与验证
│   └── 05-retrospective.md    # 最难问题、学习收获、下一步
├── <依赖文件>                # 如 requirements.txt 或 package.json
└── .env.example              # 所需变量；无变量时注明无需配置
```

本 README 当前用于梳理题目；实现完成后，应补充实际环境、安装命令、运行命令、测试命令及示例入口。

## 8. 实现前需要明确的规则

以下属于项目设计选择，原题没有规定唯一实现方式。应先在 `docs/01-requirements.md` 中定义，再据此实现和测试。

本项目的 v1 规则与验收规格见 [需求与验收约定](docs/01-requirements.md)；该文档是实现基线，不代表已经通过运行验证。

| 问题 | 需要明确的内容 |
| --- | --- |
| 截止时间 | 时间格式、时区、计算起点，以及如何结合工具耗时判断能否按时完成 |
| 费用口径 | 方案预计费用与已发生工具费用如何记录；失败、重试与替代方案如何计费 |
| 重复执行 | 如何识别同一任务；再次执行时复用、重做或返回已有结果的规则 |
| 信息不足 | 缺预算、截止时间或素材不足时，如何提示、暂停或结束 |
| 失败处理 | 哪些错误可恢复、何时选择替代方案、何时停止 |
| 执行上限 | 上限数值，以及触发上限后返回的状态和已完成结果 |

## 9. 提交前检查清单

- [ ] 按 README 的步骤可以安装并运行项目。

- [ ] 达到执行上限时，明确返回未完成状态。
